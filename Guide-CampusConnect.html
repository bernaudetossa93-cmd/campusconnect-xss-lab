CampusConnect

Repères pour installer les deux versions et comprendre les trois scénarios XSS.

Usage local uniquement. La version vulnérable est réservée à votre ordinateur. Gardez-la sur localhost et ne la publiez pas sur un réseau ou un hébergement. Les démonstrations ci-dessous ne font qu'afficher une boîte de dialogue.

1. Les deux dossiers

Version vulnérable

version-vulnerable affiche volontairement certaines valeurs sans encodage HTML. Les pages permettent de reproduire les cas réfléchi, stocké et DOM.

Dans cette copie, les points dangereux sont dans recherche.php, index.php, commentaires.php et script.js.

Version corrigée

version-corrigee garde les mêmes pages et les mêmes fonctions. Les données utilisateur sont encodées avant affichage, et le JavaScript utilise textContent.

Les corrections sont visibles dans les fichiers portant les mêmes noms.

2. Installation dans XAMPP

  1. Placez le dossier du projet dans C:\xampp\htdocs\campusconnect-xss\ (ou dans le dossier htdocs de votre installation XAMPP).
  2. Démarrez Apache et MySQL dans le panneau XAMPP. Vérifiez le port MySQL dans config.php de chaque version : ce dépôt utilise 3308 par défaut, tandis que beaucoup d'installations utilisent 3306.
  3. Dans phpMyAdmin, importez une fois le fichier database.sql depuis l'un des deux dossiers. Les deux versions utilisent la base campusconnect.
  4. Si nécessaire, adaptez les paramètres PDO dans config.php des deux versions selon votre installation XAMPP.

Adresses locales si le dossier parent s'appelle campusconnect-xss :

http://localhost/campusconnect-xss/version-vulnerable/
http://localhost/campusconnect-xss/version-corrigee/

Chaque dossier contient un fichier .htaccess qui désactive l'indexation des fichiers et limite l'accès aux connexions locales avec Apache 2.4.

3. Exemple inoffensif à utiliser

Cette chaîne ne lit et n'envoie aucune donnée. Elle sert seulement à voir si un navigateur interprète du HTML saisi.

<img src=x onerror="alert('CampusConnect local')">

4. XSS réfléchi

Le formulaire de recherche envoie q par GET. PHP reprend le terme dans la phrase de résultats de recherche.php. Dans la version vulnérable, la valeur est écrite directement dans le HTML. Dans la version corrigée, elle passe par e($terme), qui utilise htmlspecialchars.

Essai et résultat

  1. Ouvrez la recherche de la version vulnérable et collez l'exemple ci-dessus.
  2. Une boîte de dialogue apparaît dans la réponse de recherche.
  3. Refaites la recherche dans la version corrigée : le code est affiché comme texte et aucune boîte n'apparaît.

Les requêtes PDO de recherche sont préparées dans les deux copies. Elles protègent les paramètres SQL, mais la protection XSS vient de l'encodage de sortie.

5. XSS stocké

Le formulaire de publication enregistre le message dans MySQL. Le fil récupère ensuite le texte. Dans la version vulnérable, index.php l'insère sans encodage; commentaires.php fait de même pour les commentaires. Dans la version corrigée, ces valeurs passent par e().

Essai et résultat

  1. Dans la version vulnérable, publiez l'exemple inoffensif. Rechargez le fil : la boîte s'ouvre à chaque affichage vulnérable de cette publication.
  2. Créez aussi un commentaire de démonstration pour voir le même cycle sur la page des commentaires.
  3. Dans la version corrigée, le contenu est montré comme du texte.
  4. Supprimez les publications et commentaires depuis leurs pages. Pour tout réinitialiser, réimportez database.sql.

Le contenu stocké peut affecter les personnes qui consultent la page vulnérable, pas uniquement la personne qui l'a saisi.

6. XSS basé sur le DOM

Ouvrez la page « Aperçu » et ajoutez un fragment à l'adresse, en encodant les caractères spéciaux si le navigateur l'exige. Le JavaScript lit window.location.hash dans script.js. La version vulnérable écrit la valeur dans innerHTML; la version corrigée écrit le texte dans textContent.

Essai et résultat

  1. Dans la barre d'adresse, ajoutez # puis l'exemple de test après l'adresse de la page Aperçu.
  2. La version vulnérable interprète le balisage; la version corrigée affiche les caractères sans créer d'image.

Dans ce scénario, la valeur est traitée dans le navigateur. PHP ne la reçoit pas dans la requête HTTP, car le fragment n'est pas envoyé au serveur.

7. Résumé des corrections

  • Pour du texte dans une page HTML : htmlspecialchars($valeur, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8').
  • Pour afficher du texte avec JavaScript : element.textContent = valeur.
  • Conserver les requêtes PDO préparées pour les valeurs SQL.
  • Valider aussi les longueurs et les identifiants, sans confondre validation et encodage de sortie.
  • Ne jamais déployer les fichiers de la version vulnérable.
